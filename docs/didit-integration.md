# Didit 活体核验接入准备

> **状态：已废弃（待替代）**。本文记录的是早期云端试验，不作为实现基线。活体检测与人脸 1:1 比对以《技术验证》离线方案（MediaPipe 挑战式活体 + ArcFace，v2.3）为准；替代方案落地后本文删除或归档。评估结论见《5-技术验证清单.md》TV-07。

## 当前状态

`server/verification` 是服务端适配模块，不是运行中的后端，也没有连接现有界面。它实现 Didit V3 会话创建和查询，并预留统一的服务商入口；现有模拟活体流程仍然存在，不能作为真实身份核验结果。无后端、认证、受保护的数据存储及实际联调前，不要用于生产核验或自动放行。

## 准备工作

1. 在 https://business.didit.me/ 注册机构账户，在 Workflows 创建用户核验工作流并添加活体检测。记录 Workflow ID。当前适配器只接受单个活体检测节点，工作流的其他步骤及通过条件应与业务流程一致。
2. 在 Developers → API keys 创建具备会话创建、读取和媒体访问权限的密钥；按 Didit 控制台支持的最小权限限制工作流和 IP。不要把密钥写进前端、源码、Git 或聊天。媒体权限不足时参考图片可能为空。
3. 准备一台可部署服务的服务器及 HTTPS 域名、数据库和受控对象存储，确认谁维护部署及其访问权限。相关配置在服务器环境变量或密钥管理系统中保存，例如 `DIDIT_API_KEY`、`DIDIT_WORKFLOW_ID`；目前模块接受参数，尚未自动读取环境变量。
4. 与服务商确认当前免费额度、生产费用、伊拉克使用支持、库尔德语界面、活体截图的保存权限和保留期限。准备隐私说明、用户授权以及图片删除和访问控制要求。
5. NFC 仍需内政部的 SDK、读卡授权、字段与芯片真实性验证方案；不得把普通证件照片冒充可信芯片照片。

## 新后端必须完成的工作

- 在服务器调用 `createVerificationProvider({ provider: 'didit', apiKey, workflowId })`，使用随机且不含个人信息的 correlation ID 创建会话。服务端先检查登录身份和对具体家庭成员的操作权限，在数据库中绑定成员、申请、correlation ID 和 Didit session ID。会话链接只交给获授权的核验对象，避免记录链接或 token。
- 通过受保护的服务端流程定期调用 `getLiveness` 查询结果，使用数据库中保存的 session ID 和 correlation ID，不信任客户端提供的结果。页面跳转的 callback 不是结果证明；如以后使用 webhook，必须按 Didit 最新文档验证签名、时间戳及重放防护，再从服务端重新查询结果。处理超时、重复通知和并发重试。
- 适配器返回的 `referenceImageUrl` 是临时敏感地址，只能在服务端处理；不要记录、返回前端或永久保存该 URL。以防 SSRF 的受限下载方式获取图片，校验大小和类型后加密保存到受控存储，记录成员、会话、保留期限和访问审计。下载域名与权限须根据实际 Didit 环境确认。删除或过期时同步清理。图片保存失败时不得声称已保留。
- 活体 `passed` 只代表活体检测，不代表身份通过。未来芯片照片经可信读卡和真实性校验后，再调用经评估的人脸 1:1 比对。只有活体、可信芯片及双方照片比对满足业务规则，才能更新该成员的最终身份核验状态；否则维持待核验或转人工。
- 完成与现有页面、真实用户身份和持久化成员档案的集成，并在测试环境验证成功、拒绝、取消、重放、超时、跨成员访问、截图不可用、语言切换和移动端行为。当前代码没有完成这些工作。
